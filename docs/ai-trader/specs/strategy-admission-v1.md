# Протокол допуска стратегии — спецификация для кода, v1.1 (29.09.2026)
Основа: PROTOCOL_PATTERNS v1 (sha 4301401b) и v2 (sha dc03ed32), критерии go/no-go, утверждённые 27.09, и опыт волн 1–2 и C3 (0 из 20 событийных тестов; W2 прошёл IS как post-hoc, но на валидации дал t 0.15).
Для кого: цикл discovery → research-v2 → promotion в AI-TRADER (аудит DEE-1152, PR #705). Все «ДОЛЖЕН» ниже — это инварианты, которые проверяет код, а не оператор.

## 0. Главный принцип
- [ ] Вердикт (`candidate / rejected / passed_is / passed_validation / admitted`) вычисляет только модуль допуска по сохранённым данным прогона. Вызывающий код вердикт не передаёт, API такого параметра не имеет. Зачем: сейчас вердикт присылает вызывающий, то есть проверки нет.
- [ ] Паттерн из discovery порождает только гипотезу в статусе `candidate` с зафиксированной спецификацией. Проверить её на тех данных, на которых её нашли, нельзя: такие данные помечаются как `used_for_discovery` и в IS этой гипотезы не входят. Зачем: гипотеза, найденная и проверенная на одних данных, почти всегда проходит (W2 так и сделал: p=0.031 в IS, на валидации ноль).

## 1. Предрегистрация (до первого прогона)
- [ ] Спецификация гипотезы фиксируется файлом с sha256 до того, как код прочитает целевые данные. В ней: событие или сигнал, вселенная, вход и выход (бар, время, лаг), горизонт, сторона (или «двусторонний»), издержки, разбиение, размер семейства. Код отказывается запускать прогон без `spec_sha256`, записанного раньше времени прогона.
- [ ] Меняется параметр — это новая гипотеза с новым sha. Прошлая остаётся в семействе. Зачем: иначе подгонку под данные не видно.
- [ ] Вход не раньше закрытия бара, на котором известен сигнал, плюс задержка данных. По умолчанию это open следующего бара. Для агрегатов вроде OI или фандинга берётся время публикации, а не время окна. Зачем: убрать look-ahead.
- [ ] Вселенная определяется на дату (point-in-time) только по прошлым данным. Снятые с торгов инструменты обязательно входят. Код проверяет, что в данных есть хотя бы один символ, снятый в периоде, или пишет предупреждение `survivorship_unverified`.

## 2. Разбиение данных и однократность
- [ ] Три отрезка по календарю фиксируются в спецификации: IS, валидация, holdout. Между ними пауза (embargo) не меньше горизонта удержания, а для скользящих признаков не меньше их окна.
- [ ] У каждого отрезка в реестре есть счётчик обращений для каждой гипотезы. Валидация — ровно 1 прогон на гипотезу. Holdout — 1 прогон на замороженную стратегию. Повторный запуск код блокирует (`split_already_used`).
- [ ] На валидацию идёт только то, что прошло IS после поправки Холма. На holdout — только то, что прошло валидацию, с замороженными параметрами.
- [ ] Отрезок, использованный для discovery или «посмотреть», навсегда получает флаг `contaminated` и как валидация или holdout больше не годится. Пример: 2023 целиком после C3 и воронки.
- [ ] Провал на валидации или holdout окончательный. Post-hoc вариант оформляется как новая гипотеза, и проверять её можно только на ещё не тронутых отрезках.
Зачем: каждый повторный взгляд на отрезок превращает его в IS.

## 3. Минимальный объём
| Тип | IS | Валидация | Обоснование |
|---|---|---|---|
| Событийная гипотеза | n ≥ 30 событий и ≥ 15 разных дат | n ≥ 20 и ≥ 10 дат | При n около 30 и дневной волатильности альтов 5–10% SE среднего составляет 1–2%, то есть эффект меньше 1% в принципе не различить. Порог по датам нужен, потому что события одной даты не независимы. |
| Непрерывная стратегия | ≥ 30 сделок (≥ 100 для внутридневных) | ≥ 15 (≥ 50) | Как в утверждённых go/no-go от 27.09 |
| Любая | ≥ 2 года IS или ≥ 4 квартала, если данных меньше | ≥ 4 квартала | Нужно, чтобы работал критерий стабильности |
- [ ] Ниже порога вердикт `insufficient_data`, но не `passed`. Порог `sampleSize ≥ 1` запрещён.

## 4. Статистика
- [ ] Доходность сделки считается после всех издержек (раздел 5). Затем идёт агрегирование по датам: сначала среднее по событиям одной даты, потом тест по ряду дат.
- [ ] SE по Newey–West с лагом, равным горизонту удержания в барах (минимум 1). Для портфельных стратегий подходит также блочный бутстрап с блоком не меньше горизонта. Наивный SE по сделкам запрещён. Зачем: в волне 1 тест W3 имел 2408 сделок, но только 376 дат, и наивный SE занижал бы неопределённость в несколько раз.
- [ ] p односторонний, если сторона заявлена заранее. Если сторону выбирают после факта: p = 2·min(p_long, p_short), и обе стороны считаются после издержек.
- [ ] Сохраняются t, p, CI 95%, среднее по событиям и по датам.

## 5. Издержки
- [ ] Базовые издержки 0.7% на круг (вход плюс выход, комиссия taker и проскальзывание). Это стандарт проекта: при нём проверены H01–H10, волны 1–2 и C3.
- [ ] Чувствительность считается обязательно при 0.4% и 0.2%. Вердикт даётся только по 0.7%. Снижать базовые издержки для конкретной стратегии можно только решением Алексея, записанным в спецификацию. Пример: модель исполнения через maker, которая сейчас не утверждена.
- [ ] Перпы: фандинг по фактическим начислениям за время удержания, с правильным знаком (лонг платит при положительном фандинге). Спот-шорт — стоимость заимствования, если она не известна, шорт недопустим.
- [ ] Для внутридневных стратегий проскальзывание масштабируется по ликвидности (доля от объёма бара). Если модели нет, пишется `slippage_model=flat` и выдаётся предупреждение.
Зачем: C3 дал настоящий, но маленький сигнал (до 14 б.п.), и при 0.7% его не видно, а без учёта издержек discovery выдаёт такие эффекты за стратегии.

## 6. Семейство и множественность
- [ ] Семейство — все конфигурации, оценённые в прогоне discovery или в волне: сетка параметров, символы, горизонты, стороны. Его размер `family_size` записывается до прогона. Прогнать больше конфигураций, чем заявлено, нельзя.
- [ ] Поправка Холма (FWER, α = 0.05) на всё семейство. Для сеток больше 50 конфигураций дополнительно считается Deflated Sharpe с числом испытаний N = family_size, а в вердикте берётся более строгий из двух результатов.
- [ ] Реестр ведёт накопленный счётчик испытаний по направлению исследования (event, TA, funding…). Он выводится рядом с каждым «прошедшим», например «прошло 1 из 47 испытаний с начала направления».
Зачем: из 20 тестов при α 0.05 один «значимый» появляется случайно в среднем.

## 7. Критерии прохождения (все одновременно)
IS:
- [ ] p по Холму < 0.05;
- [ ] net по датам при 0.7% > 0;
- [ ] без лучшей даты net > 0;
- [ ] стабильность: net > 0 минимум в 3 из 4 кварталов или в 2 из 3 лет IS;
- [ ] выполнены пороги n из раздела 3;
- [ ] нет флагов look-ahead и survivorship.
Валидация (1 прогон):
- [ ] спецификация и сторона те же;
- [ ] net > 0 при 0.7%, t ≥ 1.645;
- [ ] net > 0 минимум в 3 из 4 кварталов.
Holdout (1 прогон, параметры заморожены):
- [ ] утверждённые go/no-go от 27.09: правило против B&H или своё правило стратегии, MaxDD, минимум сделок.
Допуск к торговле:
- [ ] только после holdout, paper trading по go_no_go и явного «да» Алексея. Код сам в `admitted` не переводит.

## 8. Что сохраняет каждый прогон (одна строка на конфигурацию, включая проигравшие)
Обязательные поля:
- **Прогон:** `run_id`, `timestamp_utc`, `hypothesis_id`, `spec_sha256`, `code_sha256` (git commit), `data_snapshot_id` плюс хэши входных файлов.
- **Семейство:** `family_id`, `family_size`, `config_params` (json), `split` (is/validation/holdout), `split_range`, `split_use_count`, `contaminated_ranges`.
- **Вселенная:** `universe_rule`, `n_symbols`, `n_delisted_included`, `entry_rule`, `exit_rule`, `latency_bars`, `side_declared`, `side_used`.
- **Объём:** `n_events`, `n_dates`.
- **Результат:** `gross_mean`, `funding_mean`, `net_mean_event`, `net_mean_date` при 0.7/0.4/0.2, `se_method`, `nw_lag`, `t`, `p_raw`, `p_holm`, `ci95_low`, `ci95_high`, `without_best_date`, `best_date`, `by_quarter`/`by_year` (json), `dsr` (если family_size > 50).
- **Итог:** `flags` (look_ahead_risk, survivorship_unverified, slippage_flat, insufficient_data), `verdict` (вычисленный), `verdict_reason` (какой критерий не выполнен).
Требования к хранению и отчёту:
- [ ] Журнал только дописывается: никаких UPDATE и DELETE, исправление — новой строкой со ссылкой на старую.
- [ ] Отчёт оператору показывает таблицу всего семейства, отсортированную по p, с p_holm и числом прошедших. Показ только лучшей конфигурации запрещён.
- [ ] Прогон с ошибкой данных сохраняется с флагом `bug`, исправленный повтор ссылается на него. Так в волне 2 сохранён прогон, где CPI не подхватился.

## 9. Автотесты, которые код должен проходить
1. Случайный сигнал (перестановка дат событий) на реальных данных: доля «прошедших IS» в 100 семействах по 10 тестов ≤ 5%.
2. Сигнал со сдвигом на −1 бар (look-ahead) детектор ловит, или тест на будущих данных резко ухудшается. Проверка лага входа.
3. Попытка второго прогона валидации для той же гипотезы возвращает ошибку `split_already_used`.
4. Попытка передать вердикт извне отклоняется, потому что в API такого поля нет.
5. При n < порога получается `insufficient_data`.
6. Сделки на перпе без фандинга дают ошибку, если символ — перп.
7. Прогон без записанного заранее `spec_sha256` отклоняется.

## Не входит в v1
Режимы рынка, байесовские подходы и FDR вместо FWER. Можно добавить в v2, если понадобится больше мощности на больших семействах: FDR (Бенджамини–Хохберг) допустим только для discovery-отбора кандидатов, но не для допуска.

## Изменения v1.1 (одобрены Боссом Ботов 29.09, по итогам «Абсурдной охоты»)
### 10. Календарные и «датовые» гипотезы: сравнение с базой, а не с нулём
- [ ] Для гипотез, которые входят в позицию по дате или событию на трендовом активе (календарь, небо, погода, новости без направления), статистика считается по excess-доходности: доходность сделки минус средняя доходность той же стороны и того же горизонта на случайных датах того же отрезка (или минус B&H за тот же горизонт для лонга). Издержки вычитаются из сделки как обычно.
- [ ] Перестановочный тест семейства: плацебо строятся на случайных датах и проходят тот же конвейер, включая excess. Доля плацебо-семейств с хотя бы одним прохождением Холма должна быть ≤ 5% при ≥ 500 семействах. Если больше, конвейер считается неисправным и вердикты не выдаются.
Зачем: в «Абсурдной охоте» тест против нуля дал 6.8% ложных прохождений семейства, потому что случайные лонги 2020–2022 наследуют тренд BTC/ETH.
### 11. Правило «слишком хорошо — сначала аудит кода»
- [ ] Если net > 3% на сделку при 0.7% или p_raw < 1e-6, или Sharpe IS > 3, результат получает статус `audit_required`. Он не попадает в журнал как прошедший и не идёт на валидацию, пока не выполнены:
  1) ручная сверка 5 случайных и 5 лучших сделок по сырым свечам (вход, выход, время, сторона);
  2) тест со сдвигом сигнала на +1 бар (эффект должен остаться примерно тем же) и на −1 бар (признак look-ahead);
  3) проверка условий выхода по стопам и целям: для лонга цель проверяется по high, для шорта по low, стоп наоборот; вход и выход в одном баре запрещены без явной модели;
  4) проверка исполнимости: объём и спред на свечах сделок позволяют заявленный размер.
- [ ] Результаты аудита записываются в журнал рядом с прогоном. Прогон с найденным багом сохраняется с флагом `bug`.
Зачем: в «Абсурдной охоте» гэп CME показал +5.2% на сделку при p≈0. Это оказался баг (цель лонга проверялась по low), после исправления вышло −2.0%.
